## Description

After this task Camera and Tool each expose exactly one public `StateFlow<…UiState>` named `state`, and the camera
package holds one type per file.

- **Camera.** `CameraStatus`, `CameraLens`, `FlashMode` and `CameraState` move word for word (KDoc included) out of
  `CameraController.kt` into one file each; `CameraController.kt` keeps only the `CameraController` interface.
  `CameraUiState` moves out of `CameraViewModel.kt` into `CameraUiState.kt` and gains the controller's
  `CameraState` as a field (`camera`), so the separate `cameraState` flow is dropped. Build it the way
  Gallery and Tool already build theirs: **one** private `MutableStateFlow<CameraUiState>` whose initial value is
  `CameraUiState(camera = controller.state.value)`, fed by a collector of `controller.state` that writes with
  `update { it.copy(camera = … ) }`, exposed with `asStateFlow()`. No `combine` and no second type.
  **Every guard keeps reading the source it reads today**: `takePicture`, `retake`, `keep`, `switchLens`, `onCleared`
  read the private flow; `cycleFlash` and `zoomBy` read `controller.state.value`, never the merged copy
  (`CameraControlsTest.zoom_changes_the_state_within_limits` calls `zoomBy` three times in a row; a merged read
  would lag by one step on a device even if the Robolectric test happened to pass). Do not reorder the steps of
  `takePicture`, `retake`, `keep`, `onCleared` (PROJECT.md: never put a state update before the file delete it
  depends on). `CameraContent(state: CameraUiState, onShutter, onKeep, onRetake, onFlash, onSwitchLens, onZoom,
  livePicture, shotPicture, modifier)`: the message rule that `CameraBody` builds from `shotFailed`/status
  (with `stringResource`) moves into `CameraContent` with identical output. `CameraBody` must keep calling
  `CameraContent`; `LivePreview` and `ShotView` stay in `CameraScreen.kt` under those names
  (`PreviewCoverageTest.EXEMPT` is path-keyed).
- **Tool.** `ToolUiState` becomes one data class `ToolUiState(tool: Tool, photoUri: String, photo: PhotoState, save: SaveState)`
  in `ToolUiState.kt`. The old sealed `ToolUiState` cases (Loading / Ready / Unreadable) become the **nested** sealed
  interface `ToolUiState.PhotoState` word for word, and the old top-level `SaveUiState` becomes the nested sealed interface
  `ToolUiState.SaveState` word for word (nested names do not end in `UiState`). `ToolViewModel` keeps one private
  `MutableStateFlow(ToolUiState(tool, photoUri))` and every write is `update { it.copy(…) }`, so a decode that finishes
  during a save cannot erase the save state. `saveState` is removed. `savedEvents: Flow<String>` (a Channel one-shot
  event) stays exactly as it is, and so do the order of its sends and the `load(maxEdgePx)` repeated-size guard
  (`ToolScreenTest` asserts the photo is asked for exactly once). `ToolContent(state: ToolUiState, onBack, onSave, modifier)`.
  Do not name anything `ToolPhoto` (it is a navigation key).
