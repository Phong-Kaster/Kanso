## Description

Replace the plain tool screen with the editor, staying in `ui/tool` (no rename: `ScreenStateTest` hard-codes the six ViewModel paths).

- Top bar: Back (description "Back", at least 48 dp), the title is the selected tool's name (exactly one Text with that name under `tool-screen`; four tests count it), Save (icon plus the text "Save"; the "Saving…" text and a progress node while saving stay as today; its indicator becomes the Expressive one in T-009). The Back and Save buttons use the Expressive `shapes` overloads where material3 1.5.0-beta01 has them.
- Middle: the photo fills the space above the controls (tag `tool-body` covers only the photo area; keep `tool-image`, `tool-unreadable`, `tool-save`, `save-message`, `TOOL_PHOTO_URI_KEY`), then the node tagged `editor-panel` showing the selected tool's own short message ending "coming in a later run." (five new strings in `strings_tool.xml`, none equal to a tool label).
- Bottom: a `HorizontalFloatingToolbar` (tag `editor-toolbar`) of five icon-only toggle buttons for `Tool.editingTools` (Edit, Remove background, Enhance, Retouch, Artistic; never `CAMERA`), each toggleable with the tool's label as content description, at least 48 dp, drawn from `Tool.iconRes` with `Icon(painterResource(...))` (never `Image`), the selected one a shape-changed toggle with animated selection (`animate*AsState` / the motion scheme; DoD 12). Bottom controls clear the navigation bar and gesture insets (`WindowInsets.navigationBars` / `systemGestures` padding), because POLICIES calls a bottom control inside the gesture zone Critical.
- State: `ToolUiState.tool` is the selected tool; `ToolViewModel` gains `selectTool(tool)` (a tool switch never reloads the photo: `FakePhotoLoader` is called once). The selected tool survives rotation (the ViewModel) and process death (DoD 23): choose the mechanism that `ToolPhotoKeyTest` proves, preferring one that keeps `ToolViewModel`'s constructor unchanged (for example a `rememberSaveable` selection in the stateful `ToolScreen` that restores through `selectTool`), else `SavedStateHandle`. `ToolScreen`'s `onSaved: (String) -> Unit` and `ToolViewModel.savedEvents` keep their signatures (the Iteration builds `Saved(selectedTool, uri)` in the nav host). The ViewModel exposes exactly one public `StateFlow<ToolUiState>`; no `var` or `Mutable…` word in `ToolUiState.kt`.
- `ToolContent` still takes the UiState; every new composable has a light and dark preview built from sample data; previews never show an endlessly moving indicator; KDoc on everything; explain the floating toolbar and toggle buttons where first used.
