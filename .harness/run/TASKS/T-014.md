## Description

Found by the fresh-context review of Phase 4 (finding 3). `NavDisplay` *seeks* the predictive transition by the gesture's progress, and the length it seeks over is set by the slowest animation, the slide spring (about 0.8 s for a pixel offset), while the fade-out of `defaultEffectsSpec` (stiffness 1 600, damping 1) is about 91 % done after 100 ms. At about 20 % of a slow swipe the screen under the finger is therefore already invisible and the screen underneath is almost in place: the person cannot "peek and change their mind" with the top screen still in sight.

Change `kansoPredictivePopTransition` so it no longer reuses the pop transition as it is: the leaving screen slides to the right **without** a `fadeOut` (it stays opaque, on top, and follows the gesture), and the screen underneath comes back the way the pop brings it (a slide from a quarter of the width on the left plus `fadeIn`, both on the same two springs read from the scheme, read once outside the lambda). It still takes the motion scheme and returns `AnimatedContentTransitionScope<Scene<NavKey>>.(Int) -> ContentTransform`; it still asks the scheme only for `defaultSpatialSpec` and `defaultEffectsSpec` (`NavTransitionTest.each_spec_takes_a_spatial_and_an_effects_spring_from_the_scheme_it_is_given` must stay green). Rewrite the KDoc of that function so it describes exactly what the function does: the top screen follows the finger and stays visible, the one underneath appears behind it, letting go carries the move on, and the predictive preview needs Android 14 or later (Android 13 takes Back through the same callback but sends no progress); the committed pop of a finished gesture still plays the full pop transition. Never write the annotation text `@Composable` in this file (PROJECT.md Constraint), and keep every name the manifest and the host use.
