## Description

Add `ScreenStateTest`, a plain JUnit test (no Robolectric) proving DoD 12 by command, so a later run cannot quietly give a screen two
state flows. It uses the same source-root convention as the other scanning tests (see `KdocCoverageTest.kt:108-119`).

1. It finds every `*ViewModel.kt` under `app/src/main/java/com/phongkaster/kanso/ui` and asserts the set is exactly
   `home/HomeViewModel`, `gallery/GalleryViewModel`, `camera/CameraViewModel`, `tool/ToolViewModel`, `saved/SavedViewModel`,
   `settings/SettingsViewModel`.
2. For each, it loads the class with `Class.forName(name, false, classLoader)` (do not initialise it; do not instantiate it) and asserts,
   with **Java reflection** (kotlin-reflect is not on the test classpath, and no dependency may be added), that it declares exactly one
   public method whose return type is `kotlinx.coroutines.flow.StateFlow`, and that the generic return type's first type argument is
   `<package>.<Screen>UiState` (Kotlin leaves wildcards out of return-type signatures). A one-shot `Flow` that is not a `StateFlow`
   (Tool's `savedEvents`) and plain read-only values are allowed beside it.
3. It scans each `…Screen.kt` and asserts that `fun <Screen>Content(` declares a parameter whose type is `<Screen>UiState`.
4. It asserts that no `…UiState.kt` under `ui/` declares a `var` or a `Mutable…` type outside comments.
5. Self-checks on **inline samples** (no helper types at the top level of the file — anonymous objects, lambdas or types nested inside the
   test class, because `OneTypePerFileTest` scans this file): the checker reports two `StateFlow`s, a `StateFlow<String>`, and a `Content`
   with no UiState parameter, and accepts the good case.
