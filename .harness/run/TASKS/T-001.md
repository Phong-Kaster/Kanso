## Description

After this task the Home, Gallery and Settings screens each get everything they show from one UiState, and each
ViewModel exposes exactly one public `StateFlow` of it, named `state`.

- **Home.** `HomeUiState.kt` holds `data class HomeUiState(val tools: List<Tool>)`. `HomeViewModel` exposes
  `val state: StateFlow<HomeUiState>` (a private `MutableStateFlow(HomeUiState(Tool.entries))` shown through
  `asStateFlow()`) and no longer has `val tools`. `HomeContent(state: HomeUiState, onToolClick, onSettingsClick, modifier)`.
  The stateful `HomeScreen` collects `state` (follow the way `GalleryScreen` collects `GalleryViewModel.state` today).
  **This is where the UiState pattern is first used, so `HomeUiState.kt` carries the explanation for a reader who has
  never met it**: a UiState is one immutable snapshot of everything a screen shows; the ViewModel produces it through
  one StateFlow; the screen never edits it, it asks through callbacks and a new snapshot replaces the old one; the
  screen reads it with `collectAsState`; and a preview can build one from sample data. Use the words "snapshot",
  "ViewModel" and "StateFlow". The other five `…UiState.kt` files point back to it ("see HomeUiState") instead of
  repeating it.
- **Gallery.** `GalleryUiState` moves out of `GalleryViewModel.kt` into `GalleryUiState.kt`, KDoc included, with one
  added field `tool: Tool` so `GalleryContent` can take the tool's name from the state (replace the separate
  `toolName` parameter; the VM seeds `tool` in its initial state). Keep the name `state` and the field names
  `loading`, `selectedAlbumId`, `photos`, `albums`: `GalleryGridTest` and `GalleryGridScreenshotTest` read
  `viewModel.state.value.loading` and wait on the others. `GalleryContent(…, state: GalleryUiState, …)` replaces the
  separate `albums`, `selectedAlbumId`, `photos`, `loading` (and `toolName`) parameters; the permission `access` and
  `answered`, the callbacks and the `thumbnail` slot stay parameters. `SampleGallery` in `GalleryScreen.kt` builds a
  `GalleryUiState` from sample data. Keep a plain `val tool` on the ViewModel only if something outside the screen
  still reads it.
- **Settings.** `SettingsUiState.kt` holds `data class SettingsUiState(val themeMode: ThemeMode, val themeColour: ThemeColour)`.
  `SettingsViewModel` drops `themeMode` and `themeColour` and exposes one
  `val state: StateFlow<SettingsUiState>` built with `combine(repository.themeMode, repository.themeColour, ::SettingsUiState)`
  then `.stateIn(viewModelScope, SharingStarted.Eagerly, SettingsUiState(ThemeMode.System, repository.defaultThemeColour))`.
  The debounce and pending-colour code (`pendingLock` through `dropPendingColour`, `onCleared`, the companion, and the
  constructor `(repository, colourSettleMillis, colourWriteScope)` with its parameter names) is **not touched**.
  Rewrite the class KDoc lines that say "one StateFlow … each" so they are true, and explain `combine` where it is first
  used. `SettingsContent(state: SettingsUiState, wallpaperAvailable, callbacks, modifier)`: `wallpaperAvailable` stays a
  parameter (it is a fact only the drawing part computes).
- **New tests** (one class per file, each with KDoc): `T/home/HomeViewModelTest.kt` asserts
  `HomeViewModel(ViewModelClearedProbe()).state.value.tools == Tool.entries` (same order);
  `T/settings/SettingsUiStateTest.kt` asserts the Settings state starts as `SettingsUiState(System, repository.defaultThemeColour)`
  and then follows `setThemeMode` and a saved colour (copy how `ThemeModeSettingsTest`/`SettingsRepositoryTest` build a
  `SettingsRepository` on this Windows host: the DataStore must be created with `createSettingsDataStore`, never the
  default file storage; wait for saved values in real time, never `waitUntil` on the store).
