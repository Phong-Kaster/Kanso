## Strategy

Three checkpoints, strictly in order, because **every task edits the same shared build files** (`gradle/libs.versions.toml`, `app/build.gradle.kts`, the wrapper) and the tree must be green between them. Splitting the toolchain from the libraries, and Material3 from the rest, is also how a moved screenshot becomes explainable: a baseline that differs after the toolchain-only step is a defect (PRD: "a changed baseline that a library change does not explain is a defect"); one that first differs after the Compose/Navigation/Kotlin step, or after the Material3 step, names its cause.

1. **T-001 (Phase 1): Android Gradle Plugin 9.4.1, libraries untouched.** Wrapper to the Gradle version AGP needs (9.6.0 floor), AGP 9.4.1, drop `kotlin-android` everywhere (AGP 9's built-in Kotlin), the Groovy `opencv/build.gradle` and the eight `core/*/build.gradle.kts` adapted to the new DSL, app `compileSdk` 37. BOM 2026.05.00, nav3 1.1.7, lifecycle-nav3 2.10.0, Material3 1.3.2/1.4.0 and **Kotlin 2.3.20** stay (Kotlin moves in Phase 2; if AGP 9.4.1 refuses 2.3.20 the error is recorded and it moves here). The Kotlin plugin version must stay the catalog's (DoD 9: removing `kotlin-android` removes the only line that put it on the classpath, so check `buildEnvironment`). Acceptance: the full command set, the nine modules in both variants and the app's `assembleRelease` (in the background) are green, and **no baseline moved**.
2. **T-002 (Phase 2): Compose 1.12.1, Navigation 3 1.2.0, lifecycle-viewmodel-navigation3 2.11.0, Kotlin 2.4.21.** BOM 2026.09.00, nav3, lifecycle-nav3, then Kotlin and the Compose compiler and serialization plugins that follow it; CameraX is already at its newest stable (1.6.2). Fix what the new APIs break. Run `verifyRoborazziDebug`; for each baseline that moved, keep its comparison image (`<name>_phase2_compare.png`), write its README line, re-record it through the wrapper (needs the human's `## Baselines` approval). Update the pins in `knowledge/PROJECT.md`.
3. **T-003 (Phase 3): Material3 1.5.0-beta01 in the app, Expressive APIs usable.** The stable BOM maps Material3 1.4.0, so the app asks for 1.5.0-beta01 above the BOM, with a comment (A-001; D-001 lets the human choose the beta BOM instead, which would re-cut this task). The engine modules stay on their own Material3 1.3.2 pin: their compileSdk 35/36 cannot consume an artifact whose AAR metadata demands compileSdk 37 (verify; if a module breaks, the minimal build-script fix is recorded). `ExpressiveApiTest` (Worker) proves the components can be used behind `@OptIn(ExperimentalMaterial3ExpressiveApi::class)`. Same baseline procedure as T-002 (`_phase3_compare.png`). Close-out: `evidence/versions.md`, `evidence/test-edits.md`, `evidence/phase-commits.md`, `evidence/catalog-coordinates.md`, PROJECT.md; the Verifier adds the Phase 3 SHA to `phase-commits.md` (a commit cannot name itself).

**Who edits what.** Build files are shared by definition (POLICIES: "dependency and lock files belong to no Worker's scope"), so **the Iteration wires the wrapper, the catalog, `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties` and `app/build.gradle.kts` itself** and runs every build. The Iteration runs at the Fast tier, and the riskiest edits of the run are the nine module scripts of T-001 (new DSL, a Groovy OpenCV script, native build settings), so **those nine scripts go to a Capable Worker** (`opus`; scope exactly `core/*/build.gradle.kts` and `opencv/build.gradle`): the Iteration passes it the AGP 9 error text each round (§6.7) and the traps listed under Known Risks. Workers are also dispatched (Capable) for what a failing build names in source or test files (T-002, T-003) and for `ExpressiveApiTest` (T-003). No task is classified Fast: each embeds a toolchain or dependency decision and a failure here is expensive (a full test run is 2-5 minutes, a release build up to 28).

**How to run things** (PROJECT.md Constraints): start every Gradle command with `cd /d/Valve/Personal/Kanso &&`, redirect it to `.harness/run/evidence/<name>.log`, run it under `timeout`, read the exit code and the summary line, never a piped one. Long commands (`assembleRelease`) go in the background and are waited on inside the turn. The wrapper must be regenerated **before** the AGP bump (Gradle 8.14.3 cannot configure AGP 9.4.1): `./gradlew wrapper --gradle-version <v> --distribution-type bin --gradle-distribution-sha256-sum <sum>` on the old wrapper, then once more under the new Gradle so `gradle-wrapper.jar` and the scripts are refreshed. The first Gradle run after the wrapper change downloads a distribution and plugins.

**The combined command set that every checkpoint ends with:** `./gradlew :app:cleanTestDebugUnitTest :app:testDebugUnitTest :app:verifyRoborazziDebug :app:lintDebug :app:assembleDebug --continue`, then the module commands of DoD 11 (T-001 and the Verifier; T-002/T-003 when a module script changed). `:app:assembleRelease` runs at T-001 and at the Verifier.

**Baseline procedure (T-002, T-003).** (1) Run `verifyRoborazziDebug`; read `results-summary.json` for the pictures that changed in **this** run (a `_compare.png` left in `app/build/outputs/roborazzi/` by an earlier run is stale: never copy one the summary does not list). (2) Copy each changed picture's `_compare.png` to `.harness/run/evidence/baseline-diffs/<name>_phase<N>_compare.png`, open it, write its README line. (3) Record only the screenshot tests: `foreman-record-baselines.ps1 -Module app -Tests "com.phongkaster.kanso.screenshots.*"` (the full suite would also run Windows-flaky tests). (4) A picture the engine cannot explain, or that looks worse: `git checkout HEAD -- <path>` (the wrapper keeps every listed path whose bytes changed, so the engine itself holds "only the explained ones"), then fix the code or the build. (5) Re-run `verifyRoborazziDebug` to exit 0 and commit the images and the baselines together. `ExpressiveApiTest` must never call `captureRoboImage`, or the recorder adds a 17th baseline.

## Known Risks

- **AGP 9 and the Groovy `opencv/build.gradle` (name each to the Worker).** (a) The new DSL has no `compileSdkVersion`, `minSdkVersion`, `targetSdkVersion` (a library takes none), `versionCode`/`versionName` (not library settings), `packagingOptions` (use `packaging { jniLibs { keepDebugSymbols += '**/*.so' } }` for `doNotStrip`), `jniLibs.srcDirs = [...]` (use `setSrcDirs`/`srcDir`), a nested `android { buildFeatures }`; `prefab` and `externalNativeBuild` need their new-DSL forms. (b) The `try { apply plugin: 'kotlin-android' }` block and the `plugins.withId('org.jetbrains.kotlin.android') { kotlin { compilerOptions { jvmTarget … } } }` block at the end go: built-in Kotlin compiles `opencv/java/src/**/*.kt` and its `jvmTarget` follows `compileOptions.targetCompatibility` (22); if the build says "Inconsistent JVM-target", set `kotlin { compilerOptions { jvmTarget … } }` unconditionally. (c) `getDefaultProguardFile('proguard-android.txt')` is unsupported from AGP 9 and `proguard-rules.txt` does not exist in `opencv/`: use `proguard-android-optimize.txt` and drop the missing file. (d) DoD 11 forbids a global opt-out flag; AGP 9.4 offers `android.newDsl.optOut=:module` per module, a last resort that leaves criterion 11 unmet.
- **The NDK.** The base build used NDK 27.0.12077973, AGP 8.13's default; no build file sets `ndkVersion`. AGP 9.4.1's default may be newer (28.x or 29.x are installed), which would change `libc++_shared.so` and strip results in the debug APK for all three ABIs, a change on the 32-bit phone that only the device walk would notice. DoD 15 compares the native library list with `evidence/base-native-libs.txt`; if it differs, set `ndkVersion = "27.0.12077973"` in `opencv/build.gradle` and `app/build.gradle.kts` (CMake 3.22.1 is the only CMake installed).
- **Other module traps.** `core/editimage`, `gallery` and `localml` set `isMinifyEnabled = true` on release, so AGP 9's R8 defaults may apply to them (DoD 11 builds every release variant); `core/localml` sets `buildFeatures { mlModelBinding = true }` with no `src/main/ml` folder (delete the line only if AGP 9 rejects it: "as far as the build requires"); the prebuilt AARs in `libs/` (`editimage`, `imageprocessor`, `localml`, `overlaybrush`) probably share a namespace with their modules, so if AGP 9 turns the duplicate-namespace warning into an error the only fix would change a module's namespace and R-class package, which is an engine **source** change that DoD 11 forbids: do not make it, report criterion 11 unmet; **(Iteration 2 found, and the plan now reads: `core/editimage`, `overlaybrush`, `imageprocessor` and `localml` have no `src/` at all, so their namespace is a build-script line, not engine source; AGP 9 did fail on exactly this, the four wrappers got their own namespaces and A-007 records the departure from DoD 11's sentence; AGP 9 also refused the empty `litert-support` shim next to `litert-support-api`, A-008)**; `core/imagecrop` sets the Compose compiler feature flag `OptimizeNonSkippingGroups`, which may warn or fail when Kotlin moves in Phase 2.
- **Kotlin plugin version.** After `kotlin-android` goes, the Kotlin Gradle plugin on the classpath is whatever AGP 9.4.1 or the Compose/serialization plugins bring. DoD 9 requires `buildEnvironment` to resolve `org.jetbrains.kotlin:kotlin-gradle-plugin` to the catalog's `kotlin`; if it does not, put the plugin on the build-script classpath (allowed by DoD 14's one exception).
- **Roborazzi 1.76.0 plugin and Robolectric 4.17 on AGP 9.4.1.** The Roborazzi pack was verified on AGP 9.0.1; 9.4.1 is untested. Failures name the library: look the symbol up (`library-docs` skill) before the second attempt.
- **Compose 1.12.1 draws differently.** Expect some of the 16 baselines to move in T-002 or T-003. Without the human's `## Baselines` approval nothing may be re-recorded and the checkpoint cannot go green: the task stays blocked on the approval, the failing comparisons are kept as evidence, and the run ends `DONE_PARTIAL`.
- **Material3 1.5.0-beta01 against engine modules built on 1.3.2.** `core/common`, `editimage` and `overlaybrush` opt into `ExperimentalMaterial3Api` while compiled against 1.3.2 and running on 1.4.0/1.5.0-beta01. A `NoSuchMethodError` in the colour picker or an editor-style module would surface in `6_settings_custom_colour.png` or a Robolectric test; the fix is a build-script line in that engine module (in scope of T-002/T-003 only when a named failure requires it), recorded in PROJECT.md.
- **Windows file locks.** A Gradle command must never start in a directory under `app/build` (Constraint). The unit-test run is 1-5 minutes warm; a first run after a wrapper change is longer.
- **Lint.** AGP 9.4.1's lint has newer checks. A new lint error in app code is fixed in the code, never baselined, suppressed or disabled (DoD 16); a lint error in engine source is not fixed (DoD 11) and would be reported.
- **Gradle floor.** AGP 9.4's notes give Gradle 9.6.0 as the minimum. If AGP 9.4.1 states a higher one, the build says so: use the number it names.
- **`ExpressiveApiTest` and CLAUDE.md's preview rule.** The rule says every `@Composable` in `app/` has a preview: the test composes only inside `setContent { }` lambdas and declares no `@Composable` function of its own.
